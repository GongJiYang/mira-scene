## 1. 音量驱动口型
- 每次播放一个 beat 时，接线方式为 `source → analyser → destination`；`fftSize` 取 512，每一帧（requestAnimationFrame）读取时域数据并计算 RMS。
- 阈值初始值：低于 0.02 为 closed，0.02–0.08 为 small，高于 0.08 为 open（写进配置，并说明这些值如何调整）；加滞回，防止口型在阈值附近来回跳。
- 播放结束、调用 stop()、或无声 beat 时，形状立即变为 closed。
- 浏览器拿不到 AnalyserNode 时（极少数情况）：退回到「speaking 时在 small 和 open 之间交替，每 120ms 切换一次」，并写日志。

## 2. 打断有序执行器 `performInterrupt(reason)`
按 `interruptPlan` 依次**同步**执行，并在每步之后打点 `performance.mark`：
1. `interrupt:start`
2. 停止音频源，同时停止反应音 → `interrupt:audioStopped`
3. 口型强制设为 closed → `interrupt:mouthClosed`
4. 时间线 `cancelTurn(旧 turnId)`；dispatch `PTT_DOWN` 或 `SUBMIT_TEXT`（reducer 会清空字幕和队列）→ `interrupt:stateCleared`
5. 表情切换为倾听、手部动作开始收回（由 B 根据 phase 推导，这一步只需确认）
6. 发送 `interrupt` 给服务端
- 原有的 store 订阅保留作为兜底，但必须是**幂等**的（重复 stop 不报错）。
- 每一步都写入 debug 事件环形缓冲区：`{t, step, turnId}`。

## 3. 可取消的时间线调度器
- 现在 core 里所有延时触发的逻辑：无声 beat 停留 1200ms、反应音淡出、手部收回结束、nudge 计时等，**统一改为**通过 `timeline.schedule({key, turnId? , storyEventId?, atMs, run})` 注册，由一个统一的定时器驱动（用 rAF 或单个 setTimeout）。
- `cancelTurn(turnId)` 取消该 turnId 下的全部命令；带 storyEventId 的命令不受影响。
- 写入 debug 事件：scheduled / fired / cancelled（附 turnId）。

## 4. 打断矩阵属性测试（主力）
- 构造一个「模拟客户端核心」：真实的 reducer（A/B/C）+ 真实的调度器 + 假音频（可控制解码完成、播放开始、播放结束的时机）+ 假音量源。
- 用 fast-check 生成随机交错的事件序列：服务端消息（beat、tts_audio、turn_end、media_ready）、解码完成、播放开始和结束、时钟推进、**在任意位置插入的打断**（PTT_DOWN 或 SUBMIT_TEXT）、nudge。
- 每个序列都断言以下不变量（运行 1000 次）：
  1. 打断执行完的那一刻，D34 的契约后置条件全部成立；
  2. 打断之后，任何属于旧 turnId 的字幕、表情、动作、音频播放事件出现的次数为 0；
  3. 照片的状态（C）不会因为打断而倒退：developing、ready、shown 仍保持原状态；
  4. 镜头状态在打断前后保持不变（用户决定：打断时镜头不动）；
  5. 音频不在播放时，口型一定是 closed。
- 另外为矩阵中的 7 种情况各写一个确定性的用例：思考中、反应音播放中、一句话说到一半、两句之间、解码中、显影中、主动开口中。
