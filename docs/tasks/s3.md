## 1. DeepSeek 适配器（D31：格式 a）
- 使用 OpenAI 兼容的流式接口，地址取 `DEEPSEEK_BASE_URL`，模型取 `DEEPSEEK_MODEL`，**关闭思考**：`thinking: {type:"disabled"}`。设置 `stream_options.include_usage=true`，usage 里与缓存命中相关的字段要写进日志。
- 增量解析：按换行切分，每一行单独 `JSON.parse`，然后产出原始对象（交给会话层的 `parseLlmBeatLenient` 处理）。容错要求：去掉 ``` 代码块包裹；去掉行首行尾的空白；一行无法解析时，**把这一行当作纯台词**（`{say: 行文本, emotion:"neutral"}`），并写一条 warning。
- AbortSignal 要直接传给 fetch，中止后迭代器必须立即结束。

## 2. 提示词（D18、第 9 轮）
- `apps/server/src/prompts/loader.ts` 读取 `prompts/rin.v1.md`：`## STATIC` 部分作为 system 消息，**逐字不变**；`## DYNAMIC` 部分用模板填充后作为最后一条 user 消息。每一轮都在日志里记录 `prompt_version`（取自文件头注释，例如 `rin.v1`）。
- 填充规则：
  - `node_label` 和 `node_guidance` 按剧情节点写（arrive：礼貌而疏离，可以主动招呼对方坐下，注意到窗外和那杯咖啡；probe：被问起时回避，但留下线索，例如「有人说过今晚会来」；reveal：可以讲出三年的信和今晚的约定；ending：回应对方今晚的陪伴，说出余韵）。
  - `advance_rule`：当 `trust≥2`、用户这轮温和地直接问起（例如问在等谁、问那杯咖啡），或者 `turn_count≥8` 时，写「允许进入 reveal」；进入 reveal 两轮之后，写「允许进入 ending」；其他情况写「现在不要推进剧情」。**最终是否推进，仍然由 story.ts 校验**（D6）。
  - `history`：最近 12 轮，格式为「客人：…」「凛：…」。
  - `user_text`：用户原话，去掉 `<` 和 `>`，最长 500 字。
- trust 规则：用户这一轮包含关心类意图时加 1（沿用 mock 的意图识别）。

## 3. Fish 适配器
- **TTS**：每个 beat 发起一次 HTTP 请求，`text` 使用导演层产出的 `ttsText`（已带情绪标签），模型取 `FISH_TTS_MODEL`（默认 `s2.1-pro-free`），`reference_id` 取 `FISH_VOICE_ID`（为空就不传），`format: "mp3"`，`latency: "balanced"`。接口细节以 https://docs.fish.audio 为准。返回 `{mime:"audio/mpeg", data}`。
- **STT**：调用 speech-to-text 接口，模型 `transcribe-1-pro`，语言 zh。上传格式**原样转发浏览器录到的 mime**（P2 还没有实测，如果文档要求特定格式，请在报告里写明）。
- 两个适配器都要支持 AbortSignal；Fish 返回 402 或 429 时抛出带 `code` 的错误（`fish_credit` 或 `fish_rate`），交给现有的降级路径处理（TTS 会变成无声 beat，STT 会回「没听清」）。

## 4. 语速体检（D30，参照 voice-workbench 的 pace_check）
- `quality/paceCheck.ts`：根据 mp3 字节数估算时长（按 CBR 128kbps 计算，并允许用配置覆盖），算出「中文字数 ÷ 时长」。正常范围是 2.6–8.5 字/秒，超出就判定为疑似漏读或杂音，**重试 1 次**；仍然超出就保留并写 warning（不降级成无声）。
- 少于 4 个字的句子不检查。

## 5. 反应音「嗯……」（第 10 轮）
- 新增脚本 `apps/server/scripts/make-sfx.ts`：在 real 模式下用 Fish TTS 合成 2–3 条短反应音（「嗯……」「唔……」「这样啊。」），输出到 `apps/client/public/sfx/react-*.mp3`。Key 缺失时，生成一段 300ms 的轻音作为占位。**生成后的文件要提交进仓库**（这样没有 Key 的人也能用）。
- 客户端：`PTT_UP` 或 `SUBMIT_TEXT` 之后，进入 thinking 的 150ms 内，随机播放一条反应音。**它必须受 `audioStopToken` 控制**，任何一次打断都能让它立即停止；第一个真实 beat 开始播放时，反应音淡出（80ms）。

## 6. 计时（Q14、D17）
- 服务端事件：`turn_start`、`stt_done`、`llm_first_beat`、`tts_first_audio`、`turn_end`，都带上距离本轮开始的 `ms`。
- 新增客户端→服务端消息 `playback_started{turnId, seq, clientMs}`：第一个 beat 的音频开始播放时上报。服务端据此算出 `first_audio_ms`（从 turn_start 到开始播放）并写入日志。
- 新增 `pnpm latency:report`：读取服务端日志（JSON 行），输出最近 N 轮各阶段耗时的 P50/P90，并标出最慢的阶段（也就是约束所在）。

## 7. 主动开口（D32）
- 新增客户端→服务端消息 `nudge{turnId}`：客户端在 B 状态机产出 nudge 时发送（turnId 递增，按一次新输入处理）。
- 服务端把它当作一轮输入，`user_text` 填「（客人安静地坐着，没有说话）」；动态后缀里加一句「对方沉默了一会儿，你可以自然地做点什么，或者轻声说一句」。这一轮**不计入 trust**。
