# 导读：题目六项要求逐条怎么做的

> 给评审看的入口文档。每一项写清楚：**怎么实现、为什么这样选、在哪能看到**。决策编号（D1–D43）对应同目录 `decisions.md`，可以点开看完整的取舍过程。
> 状态标记：✅ 已在 main　🚧 正在开发的批次（S6c / S6f / S6g），合并后更新本页。
> 角色：**忧奈**（正版商用 Live2D 皮套，深夜下播的新人主播）。早期的第一个角色「夏凛」已删除，原因见文末「后续计划 · Live2D 自动化管线」。

## 整体架构（一句话版）

```
浏览器（React 直播间）──WebSocket（统一信封 + turnId）──▶ Node 服务端
  无头核心：对话状态机 A / 表演状态机 B / 剧情媒体 C（D28）        会话 → 导演层（D29）→ Beat 时间线
  Live2D 渲染：纯函数产出每帧参数（D36）                             端口/适配器：STT · LLM · TTS · 生图（D9）
                                                                    真实：Fish STT/TTS + DeepSeek V4 Flash；Mock：本地剧本 + 预录语音
```

## 1. 页面

| 要求 | 做法 | 状态 |
|---|---|---|
| 以场景和角色为主体，不用聊天列表 | 仿直播间：画面是忧奈 + 房间背景，桌面右侧是**弹幕**（直播语境下的输入回显，不是对话记录），手机改上下结构（D40） | ✅ |
| 背景、角色、字幕、文字和语音入口 | 字幕压在画面下方；底部是弹幕输入框 + 麦克风按钮 | ✅ |
| 移动端适配，桌面可用 | 手机竖屏优先（safe-area、无横向滚动，三种视口 e2e 断言）；桌面横版 + 空格键按住说话 | ✅ |
| 待机 / 倾听 / 思考 / 说话，可从画面感知 | 状态机 A 给出阶段，Live2D 参数由纯函数按阶段计算：待机＝呼吸、眨眼、视线漂移、偶尔抱熊；倾听＝前倾、歪头、睁大眼看镜头、轻点头 + 麦克风声波；思考＝视线和头偏开 + 字幕区「……」；说话＝口型 + 情绪表情 | 待机/说话 ✅；倾听/思考的人物动作 🚧 S6f |

**为什么这样设计**：题目要求「关掉声音也能看出状态」，所以每个状态都要在**人物身上**有差别，不能只靠图标。

## 2. 文字和语音互动

| 要求 | 做法 | 状态 |
|---|---|---|
| 文字输入 | 弹幕输入框 | ✅ |
| 麦克风 | 按住说话 → 整段上传 Fish STT | ✅ |
| 语音回复 + 同步字幕 | 服务端按句流式下发 Beat，每句带 TTS 音频；字幕以**音频时钟**为准逐句出现（D34） | ✅ |
| 连续多轮 | 会话内保留完整历史，剧情节点在服务端推进（arrive → probe → reveal → ending，D6） | ✅ |
| 方案选择 | **STT + LLM + TTS 组合**，不用端到端实时语音模型（D1） | ✅ |

**为什么不用端到端模型**：端到端模型的输出是音频流，情绪、动作、镜头这些「画面指令」只能走旁路，很难和语音逐句对齐，也很难做 Mock。组合方案让每一句都是一个带视觉字段的结构化 Beat。DeepSeek 关闭思考模式、单次流式调用，首句约 0.8 秒（D31）。

## 3. 语音打断

| 要求 | 做法 | 状态 |
|---|---|---|
| 交互方式 | **按住说话（PTT）**：角色说话时按下即打断（D2） | ✅ |
| 语音立即停止 | 打断执行器在同一帧内同步执行：停音频 → 闭嘴 → 清字幕和时间线 → 切倾听脸 → 发 interrupt；实测停声 0.10ms（D34） | ✅ |
| 未完成回复失效 | 客户端分配递增 turnId（D12）；服务端收到新轮次即 abort 旧的 LLM / TTS 请求 | ✅ |
| 未播放的字幕、动作、媒体不再出现 | 时间线上的事件都是可取消调度，打断时整体清空（D34） | ✅ |
| 切到倾听并处理新输入 | reducer：speaking → listening | ✅ |
| 迟到响应不覆盖 | 所有消息带 turnId，客户端丢弃旧轮次；属性测试随机乱序验证（D3） | ✅ |

**为什么选按住说话而不是自动 VAD**：手机外放时，角色自己的声音会被麦克风收进去误触发打断，自动 VAD 必须先做回声消除才可靠。按住说话的打断时机是确定的，录屏可以 100% 复现。代价是没有自然对话那么流畅。

**一个有意的例外**：剧情图片（见 §5）只绑定剧情事件 id，不随轮次作废——打断不会让已经开始生成的图片白白丢掉（D27）。

## 4. 角色和场景驱动

**结构化指令 = Beat**（D5、D29）：每一句回复是一个 Beat：

```
{ say, emotion, hands, action, camera, fx, media, story }
```

**分两层决定，保证画面始终合法**：
- **LLM 只决定**：台词、情绪（封闭词表）、可选建议动作、可选「推进剧情」。
- **导演层（纯函数）决定其余**：动作冷却、剧情推进校验、镜头、特效、图片视频事件。LLM 输出再乱，也不会出现角色没有的动作或素材。导演层有属性测试做模糊测试。

| 最低要求 | 忧奈的实现 | 状态 |
|---|---|---|
| 3 种可辨认情绪 | 平静 / 防备 / 难过 / 温暖：参数组合 + 皮套自带表情（难过叠加哭哭和流泪，温暖叠加脸红，首句惊讶） | 参数组合 ✅；皮套表情 🚧 S6f |
| 2 种非说话动作 | 喝饮料、看手机、抱熊、看向一侧（剧本里的无声动作槽位，按冷却规则出现） | 🚧 S6f |
| 1 次背景、镜头或环境变化 | 进入 reveal：镜头推近 + 直播间灯光变暗；进入 ending：拉回全身 + 爱心飘浮；弹幕说「换个背景」→ 换场景（D41） | 🚧 S6g / S6c |
| 1 个由对话触发的明显视觉事件 | 用户聊到她的过去或安慰她 → LLM 提议推进到 reveal → 导演层校验通过 → 镜头推近、灯光变暗、开始哭、弹出**按刚才对话生成**的「第一次开播截图」 | 服务端 ✅；Live2D 舞台呈现 🚧 S6g |

**不按计时器播放**：所有视觉事件都挂在 Beat 上，由回复内容和剧情节点触发，时间以该句音频为准。待机小动作是唯一按时间触发的东西，但只在无人说话时出现，也不算题目里的「视觉事件」。

## 5. 多模态表现能力（做了三种）

| 能力 | 做法 | 状态 |
|---|---|---|
| Live2D | 正版皮套，Cubism SDK 渲染；每帧参数由纯函数产出，视线和转头统一限幅（D36） | ✅ |
| 由状态驱动的 WebM 片段 | ending 播「关推流」片段；处理加载中、播放结束、中途打断（打断后暂停淡出） | 服务端 ✅；Live2D 舞台呈现 🚧 S6g |
| 根据当前对话生成图片 | reveal 时后台生成「第一次开播截图」，提示词带入当前对话；生成中显示加载状态；失败退回预置截图，不打断剧情（D27）。弹幕换背景用参考图生图，构图由代码锁死（D41） | 🚧 S6c / S6g |

## 后续计划

### Live2D 自动化管线：尝试过，效果没达到交付标准，已放弃用于本次交付
- **想做什么**：让 AI 把一张立绘自动做成 Live2D——See-through 自动拆层并补画遮挡 → 本项目的 Python 工具重建眼睛、口型和原分辨率 → psd2live 自动绑定网格、变形器和物理（D33、D35，过程见 `live2d-pipeline.md`）。第一个角色「夏凛」就是用这条管线做的。
- **做到了哪**：迭代了 6 轮（run1–run6），每发现一个瑕疵就写一条可自动计算的指标（空洞像素、虹膜越界、残影、色差），管线能一条命令跑完并导出 Cubism 全套文件。
- **为什么失败**：自动拆层和自动绑定的质量上限不够——眼睛和口型反复出现重影、眼球露边，转头时头颈分离、动作僵硬。指标能逐条修平，但整体观感始终达不到「直播主播」的水准，继续修的投入产出比太低。
- **怎么处理**：交付改用购买的正版商用 Live2D 皮套（忧奈），删除夏凛（D43）。管线代码和记录保留。
- **以后怎么继续**：① 把手工精修沉淀成规则，扩大自动指标覆盖面；② 批量化，指标不达标的自动列给人工；③ 用 psd2live 的 MCP 接口让 AI Agent 按指标自动微调。等拆层和绑定模型本身变强后再评估。

### 其他

- 自动语音活动检测：做好回声消除之后，再提供「免按键」模式作为选项。
- 线上部署与 iPhone 真机音频验证。
