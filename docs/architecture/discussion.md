## 第 1 轮 · 第一性原理（first-principles-thinking）· 2026-10-25

**适用边界**：框架的 When NOT 包括「上线时间紧迫」。72 小时属于这种情况，所以这一轮只在「这道题本质上考什么」的层面使用，并且限定在一轮内完成拆解。

**假设清单与用户判断**
| # | 假设 | 用户判断 |
|---|---|---|
| A1 | 题目重心是打断与失效一致性 | **修正**：最花时间、最难的是 §4 角色和场景驱动 + §5 多模态表现（Live2D、Rive、Spine、序列帧等），整体视觉才是核心。用户会从中挑一个方向，**亲自审核逻辑流程**，以此展示能力；其他 5 项核心尽量整合开源项目，减少开发时间 |
| A2 | 移动端优先的网页 | 采纳，**移动端适配优先** |
| A3 | 一问一答的轮次制 | 作为挑战点 → `challenges.md` C1 |
| A4 | STT + LLM + TTS 三段组合 | 采纳 |
| A5 | 按住说话 | 采纳 |
| A6 | 指令由 LLM 直接输出 | 采纳为退路；导演层作为挑战点 → C2 |
| A7 | 服务端权威 | 采纳 |
| A8 | 没有 Key 也能体验 | 用户问这是什么意思 → 已解释（见下） |
| A9 | 评审只看录屏、README 和运行效果 | 用户有服务器，**时间来得及就部署上线**。最重要的一环：**界面里内置一个开发文档窗口**，讲开发流程、采纳了哪些方案、后续方向的进展 |

**Q1 面试官看重什么**：架构能力和 AI 交付能力。
**Q2 是否挑战 A3、A6**：挑战，但要保证有退路，效果不理想时可以补救。
**Q3 外部视角**：用户的 voice-workbench 项目可能和导演层吻合。经核查：`backend/app/speech/emotion_vocab.py` 是一个封闭情绪标签表加 Fish S2 括号指令的导演模块，已在线上运行 → 写入 C2 作为已验证的先例。
**可选扩展**：用户选定「实时语音」+ 一个由 Claude 推荐的方向（待用户确认）。

**第 2 步的基本事实**：用户认可，把 1–4 写进开发文档的第一页 → `core-truths.md`；第 5 条转化为「尽量部署上线」。

**A8 的解释**：题目 §6 原文是「提供无需私人 API 密钥也能查看核心流程的方式，例如 Mock 模式或录制回放模式」。面试官手上没有你的 Fish 或 DeepSeek Key，他们 clone 下来本地运行时，如果代码必须有 Key 才能启动，就会直接失败。部署上线（Key 放在你的服务器上）可以解决「在线看」的问题，但**本地启动仍然必须能在没有 Key 的情况下跑通**。另外，线上部署会带来两个附带问题：Key 被滥用，需要给每个会话设额度上限；额度用完时，要退回到回放或 Mock 模式。因此之前暂缓的 Mock TTS 方案 B（预录真实声音）价值上升了。

**结论 / 影响的决策**
- 核心判断修订：打断与失效是**必须做对的底线**（核心事实 1、2），**展示重心是 §4、§5 的角色与场景表现**，由用户人工主审。
- 新增 D21 开发文档窗口、D22 线上部署、D23 投入重心；新增 `challenges.md`（C1、C2）。
- 讨论计划调整：P0 增加「动画方案与开源整合选型」一轮（`decision-matrix`），放在 G1 之前。

## 第 2 轮 · 决策矩阵（decision-matrix）· §5 多模态方向择优 · 2026-10-25

**适用边界**：有 7 个候选方案且差异明显，不属于框架 When NOT 的三种情况。按框架 Don't 的要求，Claude 事先声明了自己的倾向（D7：分层立绘 + WebM），由用户审核权重。

**候选方案**：常驻角色层 A Live2D / B Rive / C Spine / D 序列帧（分层立绘）/ E 状态视频循环；事件层 E' 预制剧情片段 / F 对话生成图 / G 生成短视频。
**加权结果**（权重：可行性 25、可状态驱动 20、表现力 20、移动端 15、展示价值 15、降级演示 5）：D 4.05 > B 3.80 > F 3.75 > E 3.65 > C 3.25 > A 3.10 > G 2.90。
**敏感性分析**：可行性降到 10%、展示价值升到 30% 时，B Rive（4.10）反超 D。结论脆弱点只有一个：能否在 72 小时内做出 Rive/Live2D 角色资源。

**用户回答**
1. 权重：认可。
2. 资源制作：倾向**自己做原创角色**，用生图模型分部位生成，再拼成 Live2D 或 Rive。难度和细节后续单独讨论。
3. 「翻相机找照片」作为对话触发的视觉事件：采纳。
4. 路线图：同意。

**结论**
- 常驻角色层：**原创角色，Live2D 或 Rive 二选一（后续专项讨论）**；**退路是 D 分层立绘/序列帧**，用同一套分部位素材就能做出来，所以前期生成的素材不会白费。

- 可选扩展：E' reveal 节点剧情片段。两周演进：G 结局「那晚的回忆」短视频（异步）。
- 架构约束：导演层只输出抽象状态，渲染层可替换（D14），所以选 Live2D 还是 Rive 不影响核心。

## 第 5 轮 · 状态模式（state-pattern）· 2026-10-26

**适用边界**：状态数远超框架 When NOT 所说的「一两个状态用布尔值」。实现形式：判别联合 + reducer（Context = store，具体状态 = 联合类型的分支）。遵循框架的两条 Don't/Do：转移逻辑只集中在 reducer 一处；每次转移都写事件日志（对接 Q14 观测页）。
**关键发现**：存在三台并行状态机（参照框架案例中 XState 的并行状态）：A 对话（S1 已有）、B 表演（面部层 + 手部层 + 待机小动作）、C 剧情媒体（D27，按 storyEventId）。
**用户回答**：1）三台状态机拆分：认可；2）视觉映射：批准，后续可以动态调整；3）打断时面部立即切到倾听、手部 200ms 平滑收回：认可；4）待机 8 秒后随机做小动作：合适。
**结论**：D28；视觉映射表写入 D28，作为 S4 的验收依据。

## 第 6 轮 · 事件驱动 API 设计（event-driven-api-design）· 2026-10-26

**适用边界**：命中 When to Use「LLM 流式响应边生成边推送」；不属于 When NOT 里的单次请求-响应。
**大白话原理**：HTTP（寄信）/ 轮询（定时打电话问）/ SSE（收音机，单向）/ WebSocket（电话，双向）/ WebRTC（视频通话，传实时音频，自带回声消除）。框架 Don't「单向推送不要用 WS」不适用于本项目：打断和录音都要上行 → WebSocket 成立。
**补充项**：重连加随机抖动；心跳（15s ping，30s 没回应判定断线）；握手时鉴权（会话令牌，配合 Q12）；单条消息上限 2MB；新增剧情层消息 `media_ready{storyEventId}`（D27）。
**C1 全双工原理**：VAD（Silero 模型判断是不是人声）+ AEC（浏览器回声消除，Chrome 效果好、iOS 外放偏弱）+ 附和判别（时长阈值）。
**开源方案**：@ricky0123/vad-web（直接采用）、getUserMedia 的回声消除约束、LiveKit Agents（借鉴最短打断时长和假打断恢复）、Pipecat / TEN（借鉴轮次检测）、OpenAI Realtime 的 VAD 参数（参考默认值）。技巧：先降音量再确认打断（ducking）。
**用户回答**：1）WS 补充项：认可；2）全双工放到扩展阶段，用开关打开，复用打断入口：认可；3）iOS 外放：既提示戴耳机，也自动退回按住模式（c）；4）400ms 阈值，再加一层「嗯/对/哦」文字过滤：可以。
**另**：用户看了 P4 预览，觉得效果差。Claude 澄清这是对齐探针，不是 Live2D（动起来是 P5 的事）。核查后发现：面部贴片对齐良好；mouth_o 有色块；手势贴片残留了原图的手和横向接缝（不合格）；头发边缘有色边。→ 待 P4 跑完后派修复任务。

## 第 7 轮 · 契约式设计（design-by-contract）· 2026-10-26

**适用边界**：框架 When NOT 提到「原型阶段设计每天在变」，所以只在 3 个边界签契约，不给每个函数都加。
**三份契约**：① LLM→导演层：LLM 是不可靠的供应方，违约是常态，违约就纠正（照搬 voice-workbench `emotion_vocab.normalize()` 的做法）；LLM 只输出 say / emotion（封闭词表）/ suggest（可选，封闭动作表）/ advance（可选）。② 导演层的后置条件与不变量：每个 beat 的表情和手势都合法；每个 beat 最多 1 个动作，3 个 beat 内不重复；镜头、特效、媒体只由剧情节点触发；剧情节点只进不退；雨停只能在 reveal 之后；同时最多显影 1 张。③ 状态机→渲染层的前置条件：每个枚举值都有对应素材（测试时检查）。
**落地方式**：zod + TS 类型；fast-check 属性测试，对导演层做模糊测试（框架第 5 步）。
**用户回答**：只回了「继续」→ 4 个问题按 Claude 的推荐采用默认值（C2 作为主方案；情绪词表 6 个；动作冷却 3 个 beat；加入 fast-check），已标注，之后可以改。

## 第 8 轮 · LLM 系统设计模式（llm-system-design-patterns）· 2026-10-26

**适用边界**：框架 When NOT 写着「推理耗时超出延迟要求就不要用」。本项目 LLM 首句约 0.8–1.5s，在 Q3 的预算内，前提是流式输出、第一句足够短。
**第 1 步 集成模式**：单次流式调用 + 结构化输出。否决 RAG（内容只有几千字，提示词放得下）、微调（题目不要求）、提示链（每多一步多一次完整等待，而且框架 Don't 写明「不要搭庞大的提示链」）。用户问为什么，Claude 给出四个理由：延迟会叠加、没有需要检索的内容、故障点越少越好、导演层已经接走了「打标签」那一步。
**第 2 步**：提示词当作代码，有版本（`prompts/rin.v1.md`），每轮记录所用的提示词版本。**第 3 步**：完整对话历史 + 剧情状态放进上下文，不用向量库。**第 4 步**：关掉 DeepSeek 的思考模式（voice-workbench 的经验），超时时退回 Mock 剧本兜底。**Don't（注入）**：用分隔符包住用户输入 + 坚持人设的规则 + 导演层兜底。
**输出格式**：P1 实测 a（逐行 JSON）、b（AI SDK streamObject）、e（行内标签 `[sad]台词<act:…>`，与 Fish 标签同形，本轮新提出），去掉 c。
**用户回答**：1）认可（附上述原因）；2）同意 P1 测 a / b / e；3）超时兜底可以，**但不必做得太细，优先级往后放**；4）认可。另外同意每批验收后自动 commit（从 G1-c 开始逐批提交；G1-a 和 G1-b 合并为一个提交）。

## 第 9 轮 · 提示词工程（prompt-engineering-patterns）· 2026-10-26

**结构**：静态前缀（角色 / 边界 / 可替换的格式段 / 3 组示例）+ 动态后缀（节点说明 / 场景状态 / 历史 / 用户输入，用 `<用户>` 分隔符包住）；放在 `prompts/rin.v1.md`，不写死在代码里。
**不用思维链**：会拖慢首字，与 Q3 冲突；本任务是表演，不是推理。
**框架 Don't「指令互相矛盾」**：「不轻易谈起自己」和「必须走到 reveal」冲突 → 把「什么时候可以说」写成明确条件，并由服务端校验。
**用户关键纠正**：体验不应该像「和 AI 聊天」。→ 重新设计剧情推进：角色主动行动、环境按剧情时间推进、线索可以点击。
**用户回答**：用户身份 = **B 那位写信的听众（反转）**（用户回复「可以」，Claude 按推荐理解）；用户沉默 12 秒后角色主动行动：可以；线索点击：等 UI 设计稿，或者先简单占位、之后再改；跑题时温和拉回：可以；3 组示例（正常 / 跑题或注入 / reveal）：可以；固定用中文回答：可以。

## 第 10–11 轮（合并）· 约束理论 + 错误处理 · 2026-10-26

**约束理论**：首句延迟先测量，只攻瓶颈。第 1 步记录 4 个时间点（Q14）；第 2 步挖潜：关掉思考模式、命中前缀缓存、第一句 ≤20 字、TTS 设为 balanced；第 3 步其余环节一律不动；框架 Do 提到的缓冲：下一句 TTS 先合成好备用；第 4 步按瓶颈三选一：STT 改用 Fish 实时识别 / 精简提示词 / TTS 改用 Fish `tts/live` 流式。另加感知层面的优化：先播一句预录的「嗯……」反应音（这句也必须能被打断）。
**错误处理**：失败处理表（LLM 超时→快速失败+兜底；TTS 失败→重试 1 次后无声 beat；STT 为空→「没听清」；WS 断线→退避重连+快照；生图失败→预置照片；额度用完→Mock/回放；不做死信队列）；故障注入：用装饰器包装各个端口，开关为 `?fail=`。
**用户回答**：1）先测量再攻瓶颈：可以；2）「嗯……」反应音：可以；3）失败处理表：可以。

**插曲：Live2D 方案**
- 用户提供 psd2live（分层 PSD/图层清单 → 自动绑定 → Live2D moc3 / p2lrt），Claude 调研了同类方案（Cubism 模板、Inochi2D、Spine/Rive、Talking Head Anime、LivePortrait），推荐 psd2live 为主方案，D24 兜底。

- 用户最终决定：**更换角色**，旧角色不再使用；分层和选人由用户人工完成；Claude 只辅助验证 psd2live 能否跑通（D33）。
