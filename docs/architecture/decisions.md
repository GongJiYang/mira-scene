## 核心判断

题目中描述最细的是 **§3 语音打断** 与 **§6 不播放失效回复**；画面、情绪、视频是表现层。
因此整体架构围绕一条原则展开：

> **一次回复 = 一条带轮次编号（turnId）的时间线，可随时整条作废。**

> **第 1 轮修订（第一性原理）**：打断与失效是**必须做对的底线**；**展示重心是 §4 角色与场景驱动加 §5 多模态表现**，这部分由用户亲自主审逻辑流程，其余核心项尽量整合开源方案。评审看重的是**架构能力与 AI 交付能力**。基本事实见 [core-truths.md](./core-truths.md)，挑战方向见 [challenges.md](./challenges.md)。

## 范围策略

1. **阶段一：核心体验 100% 完成**——下方「需求对照表」每一行都达到验收标准，交付物齐全。
2. **阶段二：少量创意扩展**——仅在阶段一全部验收后，挑选极少数方向做深（候选方向另行讨论，不预先承诺）。
3. **明确不做**：题目「不需要完成」清单全部排除——匿名会话 ID 代替账号；会话状态存内存不建数据库；单角色、单场景、单章节；无后台、无支付、无原生端、不训练模型。

## D1 语音链路：STT + LLM + TTS 组合 ✅

- **Y**：在「回复需同时驱动语音与结构化场景指令」的语境下，面对「指令与台词对齐、可 Mock、可替换 Provider」，选择 **STT → LLM（流式结构化输出）→ 按句 TTS** 组合，而不是端到端实时语音模型，以达成指令天然与台词对齐、取消信号可逐段传递，接受首包延迟更高（用按句切分 TTS 缓解）。
- **备选**：端到端实时语音模型——延迟最低、自带 VAD，但输出是音频流，场景指令只能经 function call 旁路，对齐难控、难 Mock。
- **依据**：`llm-system-design-patterns`
- **Provider 落地（Fish Audio）**：
  - **STT**：Fish Audio Speech-to-Text HTTP 接口（`transcribe-1-pro`）。PTT 松开后整段上传；实时 ASR WebSocket 目前还是 Preview，核心阶段不用。
  - **TTS**：Fish Audio，**每个 beat 一次请求**（`latency: balanced`）。beat 的边界就是音频的边界，便于把指令绑定到"该句音频开始"的时刻，也能逐句取消。合成下一句与播放当前句并行，只有第一句的等待用户能感知到。
  - **角色声音**：从 Fish 音色库选一个，或用 Voice Design 生成 Mira 的声线，通过 `reference_id` 固定。音色来源写进 README。
  - **密钥**：Fish Key 只放在服务端，由服务端代理所有请求，前端永远拿不到 Key。
  - **LLM**：Fish Audio 不提供 LLM，单独实现一个 OpenAI 兼容协议的适配器，一个适配器即可覆盖多家模型服务。
  - **待验证（技术预研）**：Fish 的 `drama-3` 模型支持方括号指令，可以试试把 beat 的 `emotion` 映射到语音语气，实现"情绪同时作用于画面和声音"。验证通过就纳入，否则用默认模型。

## D2 打断交互：按住说话（PTT），说话中按下即打断 ✅

- **Y**：在「移动端外放、回声消除属可选扩展」的语境下，面对「打断必须可靠、可复现」，选择 **PTT（桌面端空格快捷键）**，而不是自动 VAD，以达成打断时机确定、录屏 100% 可复现，接受交互不如自然对话流畅。
- **备选**：自动 VAD（如 Silero VAD）——更自然，但手机外放时角色声音会误触发打断，必须先做 AEC。
- **后续**：自动 VAD、附和词识别列入扩展方向。

## D3 打断与失效：turnId 轮次隔离 ✅（核心机制）

- **Y**：在「网络可能乱序、服务端取消可能失败」的语境下，面对「旧回复不得复活或覆盖当前状态」，选择 **客户端按 turnId 过滤作为唯一正确性保证、服务端 AbortController 取消仅作资源优化**，而不是依赖服务端取消成功，以达成任何迟到事件都无法影响当前轮，接受服务端可能多消耗少量 token。
- **流程**：
  ```
  用户按下 PTT（currentTurnId = 7）
  ① 本地立即执行（不等服务端）：
     audio 队列 stop() + 清空 → 丢弃未执行的时间线指令 → currentTurnId = 8 → 状态 listening
  ② 发送 {type:"interrupt", turnId:7} → 服务端 abort LLM/TTS 流
  迟到的 {turnId:7, ...} → reducer 丢弃
  ```
- **推论**：快速连续输入走同一路径——新输入即令上一轮失效。

## D4 前端状态：单一 Store + Reducer 状态机 ✅

- **Y**：在「舞台、字幕、输入栏、视频层共享角色状态」的语境下，面对「状态可预测、可测试」，选择 **Flux 单向数据流 + 判别联合类型状态机（手写 reducer）**，而不是 XState 或组件内分散状态，以达成非法状态不可表示、reducer 可纯函数单测，接受需自行维护转移表。
- **状态**：`idle | listening | thinking | speaking(beatIndex) | error(reason, retry)`，均携带 turnId。
- **依据**：`flux-unidirectional`（多组件共享状态）、`state-pattern`（游戏角色式模式切换）、`type-driven-design`（让非法状态无法表示）。
- **否决**：完整 `event-sourcing-pattern`——超出需求；仅保留 append-only 事件日志用于排查与日后回放。

## D5 角色/场景指令：Beat 时间线 + NDJSON 流式 ✅

- **Y**：在「视觉事件不得按固定计时器播放」的约束下，面对「指令与语音同步、首句尽早播出」，选择 **每句台词为一个 beat、逐行流式下发、指令绑定到该 beat 音频开始播放时刻**，而不是整轮一次性 JSON 或独立计时器，以达成首句即可开播、事件天然跟随回复内容，接受协议需处理 seq 顺序。
- **Schema（草案）**：
  ```json
  {"turnId":8,"seq":1,"say":"其实我在等一封回信。",
   "emotion":"sad","pose":"look_down","action":null,
   "camera":"close_up","fx":null,
   "media":{"type":"video","id":"letter_reveal"},
   "story":{"advance":"reveal"}}
  ```
- **校验**：zod 校验每个 beat；非法枚举值降级为 `neutral`，不让整轮失败（借鉴 `guardrails-framework` 的输出约束思路）。
- **枚举范围**：只开放有素材的值，覆盖 §4 最低要求（≥3 情绪、≥2 非说话动作、≥1 镜头/环境变化、≥1 对话触发事件）。

## D6 剧情状态：服务端权威，LLM 只提议 ✅

- **Y**：在「需要对话触发明显视觉事件」的语境下，面对「触发与内容相关又不被 LLM 乱触发」，选择 **服务端维护剧情图 `{node, trust, flags}`，LLM 通过 `story.advance` 提议、服务端校验合法转移**，而不是让 LLM 直接决定，以达成剧情可控、视觉事件挂在节点上，接受剧情灵活度降低。
- **节点**：`arrive → probe → reveal → ending`；进入 `reveal` 才播放信件/照片剧情片段。

## D7 多模态能力：分层立绘 + 状态驱动 WebM 片段 🟡

- **Y**：在「72 小时、需展示失败降级」的语境下，面对「状态可辨认、视频需处理加载/结束/打断」，选择 **身体姿势层 + 表情层 PNG（CSS/GSAP 做呼吸、倾听前倾、思考移开视线）+ 1–2 段剧情 WebM**，而不是 Live2D 或生成式图片/视频，以达成低成本稳定表现、天然的降级展示点，接受动画精细度有限。
- **视频三态**：加载中（立绘继续）、结束（回常驻角色）、被打断（暂停并淡出）；加载失败 → 静态图 + CSS 动效（录屏中的失败状态之一）。
- **否决**：Live2D（绑骨成本过高）；生成式媒体（延迟与失败面大，列入扩展）。

## D8 传输：单会话 WebSocket + 统一信封 ✅

- **Y**：选择 **WebSocket，消息信封 `{type, turnId, seq, payload}`**，而不是 SSE + POST，以达成双向打断消息与下行流共用通道，接受需自行处理重连。
- **上行**：`text_input`、`audio_input`（PTT 松开后整段上传）、`interrupt`
- **下行**：`beat`、`tts_chunk`、`state_snapshot`、`error`
- **重连**：指数退避；重连后服务端推送 `state_snapshot` 恢复剧情与角色状态。

## D9 Provider 抽象与 Mock：端口/适配器 ✅

- **Y**：在「多个外部模型依赖、须无 Key 可体验」的语境下，选择 **STT / LLM / TTS / Media 四个端口 + 真实与 Mock 适配器**，以达成可替换 Provider、可故障注入，接受一层间接调用。
- **Mock**：LLM 用剧本 + 关键词匹配；TTS 用预录音频或浏览器 `speechSynthesis`；STT 用 Web Speech API 或文字输入。
- **故障注入**：`?mock=1&fail=llm_timeout|tts|video|ws_drop`，保证录屏中失败态稳定可复现。
- **依据**：`ports-and-adapters`（When NOT 为「简单 CRUD」，本项目不属于）。

## D10 失败处理：超时 + 角色化兜底 ✅

- **Y**：在「原型阶段」的语境下，选择 **分阶段超时 + 角色台词兜底 beat + 重试按钮**，而不是熔断器/复杂重试，以达成失败时体验不中断，接受不处理持续性故障。
- **超时**：LLM 首 token 10s、TTS 单句 8s。
- **降级**：TTS 失败 → 本轮仅字幕 + 动作；视频失败 → 静态图；iOS 首次点击解锁 AudioContext。
- **否决**：`circuit-breaker-pattern`、`retry-pattern`——依据 `error-handling-patterns` 的 When NOT：原型阶段过早引入韧性工程会拖慢迭代。

## D11 协作方式：契约优先 + 分阶段派发给执行 Agent ✅

- **Y**：在「架构师（Claude）负责讨论与验收、执行 Agent（oh-my-pi + DeepSeek V4 Flash）负责编码，且每次派发都是无记忆的独立会话」的语境下，面对「多次独立执行之间保持一致」，选择 **先固化 `packages/protocol` 作为唯一契约，每个阶段写自包含的任务说明和验收标准再派发**，而不是一次性派发整个项目，以达成每个阶段都能独立验收、偏差能及早发现，接受多一些说明文档的编写成本。
- **依据与反思**：`api-first-design` 的 When NOT 写着「前后端是同一个人时，隐式协调就够了」。但这里的情况不同：每次派发都是一个**没有记忆的新"开发者"**，相当于多个团队并行，契约优先因此成立。`schema-registry` 被否决：单团队、消息类型少于 10 种，共享一个 zod 包就够了。
- **代码组织**：服务端按端口/适配器分层（D9）；客户端围绕单一 store 按功能分目录（stage / subtitle / input / media），参考 `vertical-slice-architecture`。
- **阶段路线**：
  | 阶段 | 内容 | 验收重点 |
  |---|---|---|
  | S1 | 单仓骨架 + 协议包 + 客户端状态机 reducer + 单测 | 失效轮丢弃、打断转移等单测全部通过 |
  | S2 | 服务端 WS + Mock 适配器 + 客户端占位舞台 | 无 Key 跑通多轮对话与打断 |
  | S3 | 接入真实 Provider：Fish STT/TTS、LLM | 真实语音多轮对话 |
  | S4 | 视觉：分层立绘、四态动画、剧情图、WebM | §4 和 §5 的最低要求 |
  | S5 | 失败与降级、故障注入、移动端适配 | §6 全部条目 |
  | S6 | README、AI_USAGE、录屏脚本 | 交付物对照表 |

## D12 轮次编号由客户端分配 ✅

- **Y**：面对「打断必须本地即时生效」，选择 **由客户端分配单调递增的 turnId（随每次输入或打断一起发送），服务端只校验必须递增；收到更大的 turnId 时自动中止旧轮次**，而不是由服务端分配，以达成打断时不需要等服务端往返，`interrupt` 消息只是锦上添花，接受服务端需要拒绝不递增的 turnId。

## D13 LLM：DeepSeek V4 Flash（OpenAI 兼容）✅

- **Y**：面对「实时对话首包延迟敏感」，选择 **DeepSeek V4 Flash**，通过 D1 的 OpenAI 兼容适配器接入，以达成低延迟、低成本，接受角色扮演质量可能不如大模型（可随时换适配器配置）。
- 用户已确认使用 DeepSeek。

## D14 表现层分离：无头核心 + 视图模型契约 ✅

- **Y**：在「页面 UI 由用户另行设计」的语境下，面对「设计稿接入时不能改动核心逻辑」，选择 **无头核心（store、WS、音频、录音）+ 视图模型（`useStageViewModel()` 只暴露可读状态和 4 个意图：pttDown / pttUp / submitText / retry）**，而不是让组件直接读写 store，以达成 UI 可以整体替换，核心逻辑和测试不受影响，接受多一层映射。
- **依据**：`mvvm`（ViewModel 暴露数据流和命令）。它的 When NOT 是「无交互的只读展示」和「服务端渲染」，都不适用于本项目。
- **推论**：S2–S3 只做占位 UI（文字显示状态和指令），用来验证核心；正式视觉等用户的设计稿出来后，在 S4 接入。

## D15 推进顺序：骨架 → 最难部分 → 视觉 ✅

- 用户指定：先完成整体骨架（S2），再集中攻克最难的部分（S3：真实语音链路 + 端到端打断），视觉由用户单独设计。
- **最难部分的判断**：结构化 beat 的流式生成与解析、Fish 按句 TTS 流水线、打断信号贯穿真实网络、移动端录音格式差异、首句延迟。这些都是端到端的不确定性；视觉的风险低，而且可以并行做。

## D16 S3 拆成「预研 S3a → 接入 S3b」，用决策矩阵加实测数据选型 🟡

- **Y**：在「外部服务的真实表现未知」的语境下，面对「流式结构化输出方案选哪个」，选择 **先写独立预研脚本实测，再用加权决策矩阵打分**，而不是凭经验直接选，以达成选型可审计（面试时能直接展示数据），接受多花约半天。
- **候选方案**：a 每行一个 JSON、逐行流式解析；b JSON 模式整体输出；c 每个 beat 一次工具调用；d 纯文本流 + 另行打标签。
- **矩阵标准与权重**：首句延迟 40%、格式合规率 30%、实现复杂度 15%、取消友好度 15%。
- **依据**：`decision-matrix`。它的 When NOT 是「时间紧迫」，所以矩阵保持轻量（4 个方案 × 4 个标准），不开评审会。
- **预研范围**：DeepSeek 流式输出（方案 a 和 b 实测，c 和 d 只做定性评估）；Fish STT 是否接受 webm/mp4；Fish TTS 首包延迟与 mp3 格式；`drama-3` 的情绪指令效果；Mira 的候选音色试听（由用户挑选）。

## D17 延迟：只优化瓶颈环节，用一个客户端指标衡量 🟡

- **Y**：面对「首句延迟要尽量低」，选择 **先实测各环节耗时、找出唯一的瓶颈、只投入在瓶颈上**，而不是 STT、LLM、TTS 三处平均用力，以达成用有限的 72 小时换最大收益，接受其他环节暂时不优化。
- **依据**：`theory-of-constraints`（先找出约束，再充分利用约束）。反思：TOC 本来针对吞吐量，这里把它借用到延迟的关键路径上，思路相同：瓶颈之外的优化对整体没有收益。
- **衡量指标**：只定义一个 SLI，**「松开按钮 / 发送文字 → 第一句音频开始播放」的 P50**，在**客户端**测量（贴近用户体验），目标 < 3s。不定 SLO，也不做错误预算。
- **依据**：`service-level-indicators`（第 2 步：选贴近用户体验的指标）。它的 When NOT 是「埋点基础设施还不存在」，而 S2 已有结构化日志，成本很低，所以适用。

## D18 提示词结构：静态前缀 + 动态后缀（为缓存而设计） ✅

- **Y**：面对「每轮都会重复发送很长的人设和格式规则」，选择 **把人设、格式规则、少量示例放在最前面并保持逐字不变，把剧情节点、场景状态、历史和用户输入放在最后**，而不是把场景状态写进系统提示开头，以达成命中 DeepSeek 的前缀缓存、降低首 token 延迟和成本，接受提示词组织方式受到约束。
- **依据**：`prompt-caching-strategies`。它的 When NOT 正好是反例「每次请求的系统提示都不同」，所以**动态内容绝不能放进前缀**。
- **这是重新走 SDFrame 流程后才发现的点**，第一版讨论里漏掉了。

## D19 输出校验：只做格式层，内容层不验 ✅

- **Y**：面对「LLM 输出是否可信」，选择 **只做格式层校验：schema 加宽松降级（已由 `parseBeatLenient` 实现）+ 提示词格式回归测试**，而不是做内容事实核查，以达成格式可靠、角色表达自由，接受台词质量只能靠人工把关。
- **依据**：`ai-output-verification` 只采用第 1 层（schema 校验），因为它的 When NOT 是「创意写作」，不需要事实核查。`prompt-testing` 的 When NOT 也是「创意类、输出多样性本来就是想要的」，所以**只测格式，不测内容**。
- **S3 验收**：20 条固定输入，解析成功率 ≥ 95%，枚举值合法率 ≥ 95%，第一个 beat 不超过 20 个字。

## D20 TTS 失败降级：空对象，复用无声 beat 路径 ✅

- **Y**：面对「某一句 TTS 失败」，选择 **用空对象（Null Object）替代：失败的那一句变成无声 beat，字幕和动作照常播放，同时给出一条不打断体验的提示**，而不是让整轮报错，以达成降级逻辑零新增代码路径（S2 的调度器已支持无声 beat），接受这一句没有声音。
- **依据**：`null-object-pattern`。它的 When NOT 是「null 本身意味着必须中止的错误」，而 TTS 失败不需要中止，所以适用。题目要求「提供基本反馈」，因此要附带提示。
- **否决**：`multimodal-pipeline-design`（面向多模态骨干模型；本项目只是编排 3 个 API，而且它的 When NOT 包含 MVP）；`chaos-engineering`（偏重，S5 只做轻量的 `?fail=` 注入）。

## D7 修订（第 2 轮 · decision-matrix）：原创分层角色 + 对话生成图 🟡

- **Y**：在「视觉是展示重心、用户亲自主审」的语境下，面对「§5 四个方向不能全做」，选择 **常驻层用原创角色（生图模型分部位生成，再拼成 Live2D 或 Rive；退路为分层立绘/序列帧），事件层用对话触发的生成图（"翻相机找照片"）**，而不是视频循环或实时生成视频，以达成状态可驱动、移动端流畅、AI 交付能力可展示，接受角色资源制作成本高、需要专项讨论。
- **依据**：`decision-matrix`。加权与敏感性分析见 discussion.md 第 2 轮；结论的唯一脆弱点（资源制作可行性）通过「同一套部位素材可降级为分层立绘」消解。
- **生成图要求**（题目 §5）：显示生成中状态（由角色翻相机的动作和台词承接）、失败退回预置照片、生成内容与当前对话相关。
- **路线**：72h = 原创角色 + 生成图；扩展 = reveal 剧情片段；两周 = 结局短视频。
- **待专项讨论**：Live2D vs Rive 的选择、部位拆分方案、生图的角色一致性（发型、雨衣、星星发夹）。

## D24 角色实现：代码绑定的 2.5D 角色（PixiJS 网格变形 + JSON 配置）🟡

- **Y**：在「用户提供分层原画、AI 负责制作」的分工下，面对「Live2D / Rive 的核心产物（.moc3 / .riv）都要在专有编辑器里手工绑定，AI 无法生成」，选择 **用分层 PNG + PixiJS 网格变形 + JSON 配置的代码化角色系统（呼吸、眨眼、视线、头部摆动、口型、情绪切换都由代码驱动）**，而不是 Live2D 或 Rive，以达成全部制作环节都能由 AI 生成、审查和测试，并对应题目扩展项「配置驱动的角色资源和动作系统」，接受细腻程度不如专业 Live2D 绑定。

## D27 生图是剧情层事件：后台异步生成，以拍立得显影的方式呈现 🟡

- **Y**：在「生图要 30–60 秒，而对话不能被卡住」的语境下，面对「生成等待和被打断时怎么处理」，选择 **后台异步任务（storyEventId 只和剧情绑定，不跟当前轮次绑定，不受 turnId 作废影响），呈现时用"拍立得显影"这个剧情内动作：先放上一张空白相纸，生成完成后显影，失败就显影成一张预置照片；只在角色不说话的空档展示**，而不是同步等待，也不让它跟着轮次被作废，以达成等待本身就是表演、失败时用户无感（Q8），接受 D3 的轮次隔离要多出一个有意为之的例外。
- **例外的边界**：只有 `media_ready` 这类剧情层消息不按 turnId 过滤，改按 storyEventId 去重；台词、动作、TTS 仍然严格按 turnId 过滤。
- **组合**：A 显影（主方案）+ C 下一次停顿时主动提起（等待过长时的补充）。B 背面朝上放在桌上作为备选。
- **依据**：`cynefin-framework`（生图延迟属于复杂域，P6 实测后再定 API）。

## D28 三台并行状态机：对话 A / 表演 B / 剧情媒体 C ✅

- **Y**：在「展示重心在角色表演（§4/§5），生图又是剧情层事件（D27）」的语境下，面对「状态之间相互纠缠、异步事件多」，选择 **把状态拆成三台并行状态机，转移逻辑全部集中在 reducer，每次转移都写事件日志**，而不是在一台状态机里塞进所有字段，也不是把转移逻辑散落到各个组件里，以达成每台都能单独测试、打断语义清晰，接受多维护两台状态机的转移表。
- **依据**：`state-pattern`（Do：事件日志形成审计轨迹；Don't：转移逻辑不要分散到多处）。
- **关系**：A 驱动 B；C 只有在 A 不处于 speaking/listening 时，才能从 ready 转到 shown。
- **视觉映射（用户已批准，后续可动态调整，建议做成配置文件）**：
  | A 状态 | 面部 | 手部 | 其他 |
  |---|---|---|---|
  | idle | 中性 + 每 2–6s 随机眨眼 + 呼吸 | cup | 超过 8s 随机小动作（看窗外 / 喝咖啡 / 看手机） |
  | listening | 看镜头 + 前倾（头部网格前移、轻微放大） | 保持 | 嘴闭合 |
  | thinking | eyelid_half + 视线偏开 | 保持 | 超过 2s 补一次「抿咖啡」 |
  | speaking | 跟随 beat.emotion；嘴部按 closed/small/open 循环 | 跟随 beat.action | 字幕 |
  | error | brow_raised | cup | 重试按钮 |
  - 情绪对应：calm = 中性；guarded = eyelid_half；sad = brow_sad + mouth_sad；warm = mouth_smile + blush；surprised = brow_raised + mouth_o。
- **异步事件对（两种到达顺序都已定义）**：打断 × 手部动作 → 面部立即切换、手部 200ms 收回；图片 ready × speaking → 排队等本轮结束；ready × listening → 等下一次 idle；显影中 × 新一轮开始 → 不作废，继续显影。
- **影响 S1 代码**：现有 reducer 就是 A；B、C 要新增。G1 时复核。

## D8 复核（第 6 轮）：WebSocket 保留，补齐连接生命周期 ✅

- 依据 `event-driven-api-design`：保留 WS（双向：打断、录音上行），否决 SSE + POST（打断和台词流分在两条通道，到达顺序更难控制）。
- 补充：重连退避加随机抖动；心跳 15s ping、30s 无响应判定断线；握手时用会话令牌鉴权（配合 Q12）；单条消息 ≤2MB；新增剧情层消息 `media_ready`（D27）。

## C1 落地（第 6 轮）：免按住模式 = vad-web + 降音量确认 + 文字过滤，作为扩展开关 ✅

- 在浏览器端用 `@ricky0123/vad-web`（Silero VAD）检测人声，配合 getUserMedia 的 `echoCancellation` / `noiseSuppression` / `autoGainControl`。
- 检测到人声 → 角色音量降到 20%（ducking）→ 人声持续 ≥400ms 且识别文本不属于附和词（嗯/对/哦…）→ 走 `PTT_DOWN` 打断路径（状态机不改）；否则恢复音量继续播放（借鉴 LiveKit 的假打断恢复）。
- iOS 外放：提示戴耳机 + 自动退回按住模式。按住模式仍然立即停止（Q1 ≤150ms）。

## D29 导演层（C2 落地）+ 三份契约 ✅（默认值，用户回复「继续」）

## D32 剧情与「不像和 AI 聊天」的三个机制 ✅

- **用户身份**：B，用户就是给《雨声信箱》写了三年信、从没露过面的听众，凛不知道。结尾的高光是：用户说出信里的一句话，她认出了他。
- **节点**：arrive（暴雨、桌上没人动的咖啡、疏离）→ probe（雨势变小、打烊提醒、只给线索不点破；用户每关心一次 trust +1）→ reveal（雨停、镜头推近、拍立得里的信、讲出三年的信和今晚的约定）→ ending（灯暗下来；用户说出信里的句子 → 认出 / 余韵）。
- **进入 reveal 的条件**：trust ≥ 2，或用户温和地直接问起；保底：第 8 轮以后以「快打烊了」为剧情理由主动说出来。
- **三个机制**（由导演层和状态机 B 实现，不增加 LLM 调用）：① 用户沉默 12 秒，角色主动行动或开口；② 打烊、雨势按剧情时间推进；③ 线索点击（咖啡、拍立得），先简单占位，等 UI 设计稿确定后再改。
- **提示词**：结构见第 9 轮；正文由 Claude 在 S3 任务中起草，用户审阅。固定使用中文；不用思维链。
