# 会话交接（session-handoff）

**原则**：交接靠文件，不靠对话记忆。`PROGRESS.md` 由项目根目录的 `CLAUDE.md` 用 `@PROGRESS.md` 引入，
所以每次新会话开头都会自动加载，不需要用户再解释一遍。
自动 compact 的摘要又长又不准；这份文件只有几百字，比摘要更可靠。

## 一、存档（会话结束前 / 每批提交后）

1. 用 `git log --oneline -5` 和 `git status --short` 核对事实。**只写已经验证过的结论**，不要凭印象写。
2. **整份重写** `PROGRESS.md`，不要往后追加。**总长 ≤ 60 行**，超出就删掉最旧的已完成项（历史在 git log 里，不用重复）。
3. 固定结构如下，不能缺任何一节：

```markdown
# PROGRESS（更新于 YYYY-MM-DD HH:MM，最新提交 <hash>）

## ▶ 下一步（新会话直接从这里开始）
<一句话，具体到第一个动作。例：【S5 · 关卡 1/9】调用 mira-code-gate + sdframe，提出 S5 的 5 个关卡问题>

## 当前位置
<批次 · 关卡 n/9 · 名称>；<这一批已做 / 未做的部分>

## 已完成（最近的在前，最多 8 行）
| 批次 | 结果 | 提交 |

## 排队（按顺序）
1. …

## 关键决策（只写会影响下一步的；完整记录见 docs/architecture/decisions.md）
- …

## 待用户处理（阻塞项）
- …

## 不要碰
- <别的会话或用户自己在改的文件，例如 tools/live2d-pipeline>
```

4. 同时更新 `docs/checklist.md`（题目对照表）：按本次核实的结果改 ✅/🟡/⬜ 和总览计数、更新日期与提交号。
5. 写完把 **「▶ 下一步」那一行原文**贴给用户，并提醒：可以 `/clear` 了。
6. `PROGRESS.md` 改动不需要单独提交，跟下一批代码一起提交即可；用户要求时再提交。

## 二、接续（新会话开头）

1. `PROGRESS.md` 已经通过 CLAUDE.md 加载。如果上下文里没有（比如不是在项目目录启动的），就用 Read 读 `~/mira-scene/PROGRESS.md`。
2. 用 `git log --oneline -1` 核对提交号。**不一致时**，说明上次没存档就结束了：先看 `git log` 和 `git status` 补齐，再报告。
3. 第一条回复只说三件事，不超过 5 行：
   - 现在在哪：`【批次 · 关卡 n/9 · 名称】`
   - 下一步：照搬「▶ 下一步」
   - 阻塞项：「待用户处理」里还没解决的
4. 然后**直接做下一步**，不要问用户「要继续吗」。只有当下一步本身就是等用户决定（比如关卡审批）时，才停下来等。

## 三、省上下文的配套习惯（存档时顺手提醒用户，不强制）

- 一个会话只做一批：一批提交后就存档，然后 `/clear`。
- 离开很久再回来：直接 `/clear` 加接续，不要续上已经很长的旧会话。
- 需要压缩时手动 `/compact` 并说明要保留什么，例如 `/compact 只保留 S5 关卡结论和待办`，不要等它自动压缩。
- 大范围搜索、读日志、跑测试交给子代理或 `| tail -50`、`grep` 过滤后再看；读文件只读需要的行范围。
- 长期不变的约定（命令、目录、铁律）写进 CLAUDE.md；会变的进度写进 PROGRESS.md。两者不要混在一起。
